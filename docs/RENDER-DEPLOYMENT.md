# Render deployment — TyagiJI Learning Platform

This repository can run as a **single Render web service**: Render builds the React/Vite client, then the Express server serves the built client and `/api/v1` from the same origin. Same-origin deployment is the simplest option for HTTP-only login cookies.

## Before deploying

1. Back up the existing MongoDB Atlas database and keep the backup outside this ZIP.
2. Confirm which database your current live website uses. Preserve its exact `MONGODB_URI` if this deployment must use existing users, courses, progress, and other records. The example database name is not a migration.
3. Do not run `npm run seed` against production until you have reviewed the seed script and confirmed its upsert behavior for your actual database.
4. Push this project to a private or public Git repository you control.

## Deploy with Render Blueprint

1. In Render, choose **New → Blueprint** and connect the repository containing `render.yaml`.
2. Review the service configuration before creating it.
3. Enter your existing MongoDB Atlas connection string for `MONGODB_URI`. Use the same database only if you intend to preserve and continue using its data. Restrict Atlas network access and use a least-privilege database user.
4. Render generates `SESSION_SECRET`. Do not replace it with a short or predictable value.
5. Deploy. The build command is `npm ci && npm run build`; the start command is `npm run start:prod`.
6. Check `https://YOUR-SERVICE.onrender.com/api/v1/health`. The root URL should serve the React website after the client build succeeds.
7. If you use a custom domain or a separate frontend host, add its exact origin to `CLIENT_URL` in Render. Comma-separate multiple origins. For the single-origin blueprint, `CLIENT_URL` is not needed for same-origin requests.
8. Create the first administrator only after deployment, using the documented `npm run admin:create` command in a trusted environment with the production database URI and strong one-time admin credentials. Never place credentials in source control.

## Production environment

- `NODE_ENV=production`
- `MONGODB_URI=<your existing Atlas URI>`
- `SESSION_SECRET=<random secret of at least 32 characters>` (generated by Render in the Blueprint)
- `COOKIE_SECURE=true`
- `TRUST_PROXY_HOPS=1` for the normal single Render proxy hop
- `VITE_API_URL=/api/v1` (build-time value in the Blueprint)
- `CLIENT_URL=https://your-frontend-origin.example` only when a separate frontend origin is used

## Rollback

Keep the prior Render deployment available for rollback. If the new release fails health checks or authentication tests, roll back the deployment and inspect logs before changing the database. Do not delete Atlas collections or replace the production database as a troubleshooting shortcut.

## Limits of this ZIP verification

The server test suite can be run locally. The client test/build require a complete platform-specific npm install (`npm ci`); this working environment's copied `node_modules` archive was missing Rollup's Linux optional package, so a successful client build was not claimed. A real Render deployment, production Atlas connectivity, and live login flows must be verified in your Render account.
